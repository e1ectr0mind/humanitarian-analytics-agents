# Дизайн: Коннекторы Kobo/Ona + агент очистки данных (ломоть 2а)

**Дата:** 2026-09-07
**Статус:** утверждён (секции 1–4 согласованы в брейншторм-сессии)
**Подпроект:** 2а из декомпозиции платформы (см. ниже)
**База:** ядро подпроекта 1 — `docs/superpowers/specs/2026-09-07-core-analyst-agent-design.md` (реализовано, master)

---

## 1. Контекст

Подпроект 2 платформы («Данные») разрезан на два ломтя, каждый со своей спекой:

- **2а (этот документ):** ODK-коннекторы (KoboToolbox API, ona.io API) + агент
  очистки/валидации. Токен-базированная авторизация, быстрый путь к ценности.
- **2б (позже):** SharePoint через Microsoft Graph — другой профиль риска
  (OAuth-приложение, корпоративный тенант IMC, возможное согласование с IT).

У пользователя есть рабочие аккаунты и в Kobo, и в Ona — live-проверка возможна.
Ключевое требование: **пользователь агента сам вводит свои данные подключения**
(сервер, токен); ничего не зашивается в код или конфиг репозитория.

## 2. Цели и границы

Три возможности поверх существующего ядра:

1. **Подключение источников.** `haa connect kobo|ona` — интерактивный ввод:
   имя профиля, URL сервера, API-токен (через `getpass`). Токен уходит в
   Windows Credential Manager (библиотека `keyring`), метаданные профиля —
   в `workspace/connections.toml`. Профилей может быть несколько.
2. **Загрузка данных.** Из чата (оркестратор вызывает инструмент) или
   `haa pull <профиль> --form <id|имя>` (без LLM). Данные ложатся в
   `workspace/data/<form>.xlsx` — дальше работает весь конвейер подпроекта 1.
   В контекст LLM попадает только сводка (файл, форма, число строк).
3. **Агент очистки** — вторая роль в реестре агентов. Производит два артефакта:
   `workspace/data/<dataset>_clean.xlsx` (сырой файл неприкосновенен) и
   `workspace/reports/<dataset>_cleaning_report.md` (что нашёл / исправил /
   пометил, числа до/после).

**Наследуется без изменений:** PII-граница (сырьё скачивается только локально),
телеметрия, бюджет, 3-strike-лимит, честность промптов.

**Не входит в 2а:** SharePoint (2б), синк по расписанию, incremental-синк
(v1 перекачивает форму целиком), межисточниковая дедупликация, запись данных
В Kobo/Ona (только чтение).

### Требование уникального идентификатора записи

Каждая запись обязана иметь явный уникальный ID:

- коннектор при сохранении использует `_uuid`/`_id` из API источника;
- при их отсутствии добавляет колонку `_haa_row_id` — детерминированный хеш
  содержимого строки + индекс вхождения для полных дублей (дубль остаётся
  видимым, ID остаётся уникальным);
- чистильщик первым пунктом чек-листа проверяет наличие уникального ID
  и создаёт его в чистой копии, если нет, с пометкой в отчёте.

## 3. Архитектура и компоненты

```
src/haa/
├─ connectors/                    ← НОВОЕ: чистые Python-клиенты, без LLM
│  ├─ base.py                     ← протокол ODKConnector + RemoteForm,
│  │                                 PullResult + ConnectorError
│  ├─ kobo.py                     ← KoboConnector (Kobo API v2)
│  ├─ ona.py                      ← OnaConnector (Ona API v1)
│  └─ credentials.py              ← профили + токены (keyring)
├─ core/
│  ├─ tools/sourcetools.py        ← НОВОЕ: SourceToolbox + MCP-сервер "sources"
│  └─ agents/cleaner.py           ← НОВОЕ: CLEANER_PROMPT + build_cleaner
└─ cli/app.py                     ← + connect / connections / pull
```

| Компонент | Обязанность | Ключевые интерфейсы |
|---|---|---|
| connectors/base | единый контракт ODK-источников | `ODKConnector`: `list_forms() -> list[RemoteForm]`; `pull(form_id, dest_dir) -> PullResult` (путь + число строк) |
| connectors/kobo, ona | реализации под конкретные API (эндпоинты, пагинация) | конструктор `(base_url, token)`; HTTP — `httpx` с таймаутами |
| credentials | метаданные в `workspace/connections.toml`; токены ТОЛЬКО в Credential Manager (сервис `haa`, аккаунт = имя профиля); fallback — env `HAA_TOKEN_<PROFILE>` | `save_connection`, `load_connection`, `list_connections`, `delete_connection` |
| SourceToolbox | второй in-process MCP-сервер `sources` по образцу DataToolbox; телеметрия каждого pull | `mcp__sources__list_connections`, `..._list_remote_forms`, `..._pull_form` |
| cleaner | вторая агентская роль: MEAL-чек-лист, pandas в сандбоксе | `build_cleaner(config) -> AgentDefinition`; инструменты — data-сервер |
| CLI | connect (интерактив, getpass), connections (список), pull (без LLM) | — |

**Инструменты по ролям:** оркестратор += `sources`-инструменты; аналитик — без
изменений; чистильщик — data-инструменты. `HaaConfig` += свойство `reports_dir`
(`workspace/reports/`, создаётся при загрузке конфига).

### Поправка к спеке §5 подпроекта 1 (PII)

`load_dataset()` получает явный флаг `include_pii: bool = False` — то самое
«осознанное ограничение v1», которое теперь реализуется, потому что стало
load-bearing: чистая копия обязана сохранять все колонки (телефоны нужны для
верификационных звонков — терять их при очистке нельзя).

Граница по сути не ослабляется: файл остаётся локальным (граница — про контекст
LLM, а не про диск); фильтр вывода по-прежнему редактирует телефоны/GPS в stdout;
промпт чистильщика запрещает печатать PII-значения (только счётчики); каждый
вызов с флагом логируется в телеметрию отдельным событием `pii_access`.
Промпт аналитика флаг не упоминает.

## 4. Потоки данных

**Pull:** `haa pull imc-kobo --form beneficiaries` (или чат → оркестратор →
`pull_form`) → `load_connection` (URL из toml, токен из Credential Manager) →
`list_forms()` для резолва имени → скачивание с пагинацией →
`workspace/data/beneficiaries.xlsx` (с гарантированным ID-столбцом) → сводка
«beneficiaries.xlsx, 3 214 строк». Телеметрия: событие `pull` (профиль, форма,
строки, длительность). Повторный pull перезаписывает файл; кэш профилей
`DataToolbox` инвалидируется по mtime файла (доработка `_ensure_profiled`).

**Очистка:** «почисти beneficiaries» → оркестратор делегирует чистильщику →
профиль → чек-лист (уникальный ID; дубли; невозможные значения; будущие даты;
разнобой категорий; пропуски ключевых полей) → pandas-код через `run_analysis`
с `load_dataset(..., include_pii=True)` (событие `pii_access`) →
`beneficiaries_clean.xlsx` + `reports/beneficiaries_cleaning_report.md` →
ответ числами: строк было/стало, дублей удалено, исправлено/помечено.
Чистая копия автоматически видна `discover_datasets` — аналитик может сразу
работать с ней.

## 5. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| сеть/таймаут | до 2 ретраев с бэкоффом в коннекторе; дальше дружелюбное сообщение (`ConnectorError` → текст, не трейсбек) |
| 401/403 | «токен не подходит, обновите: haa connect <профиль>» |
| формы нет | сообщение со списком доступных форм |
| пустая форма | честное «0 сабмишенов», файл не создаётся |
| keyring недоступен | инструкция про fallback `HAA_TOKEN_<PROFILE>` |
| ошибки очистки | наследуют ядро как есть (3-strike, честный отказ) |

## 6. Тестирование

- **Юнит без сети:** коннекторы против замоканного HTTP (`respx`) с записанными
  обезличенными фикстурами реальных ответов Kobo v2 / Ona v1; credentials против
  in-memory keyring-бэкенда; `_haa_row_id` (детерминизм, полные дубли);
  SourceToolbox (сводки без сырых данных); CLI-парсер.
- **Live-тесты** с меткой `remote` (по образцу `api`): по одному smoke на
  реальные Kobo и Ona; исключены из CI, запуск вручную.
- **Эвал чистильщика** (метка `api`): демо-датасет с известными дефектами —
  чистая копия ровно 3000 строк, 0 дублей, 0 возрастов-999; отчёт содержит
  правильные числа (посчитанные в тесте независимо pandas).
- CI без изменений (офлайн-тесты).

## 7. Критерии приёмки

1. `haa connect kobo` → профиль создан, токен в Credential Manager, в файлах
   репозитория и workspace токена нет.
2. `haa pull <профиль> --form <имя>` скачивает реальную форму в
   `workspace/data/`, файл содержит уникальный ID-столбец.
3. Из чата: «подтяни данные из Kobo по форме X» — работает через оркестратор,
   в телеметрии событие `pull`, в контексте LLM нет сырых строк.
4. Из чата: «почисти датасет X» — появляются `X_clean.xlsx` и
   `reports/X_cleaning_report.md`; сырой файл байт-в-байт не изменён;
   на демо-датасете чистая копия = 3000 строк без известных дефектов.
5. Событие `pii_access` в телеметрии при каждом `include_pii=True`.
6. Юнит-тесты и ruff зелёные в CI; `remote`- и `api`-тесты проходят локально.
