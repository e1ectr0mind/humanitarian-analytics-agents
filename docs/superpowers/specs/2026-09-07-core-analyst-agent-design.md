**Подпроект:** 1 из 6 (см. «Контекст платформы» ниже)

## 1. Контекст платформы

Целевая система — мультиагентная платформа аналитики данных для гуманитарной
организации (контекст IMC: Kobo-экспорты, программные индикаторы, MEAL/5W-отчётность,
Power BI). Главный приоритет проекта — **портфолио/карьера**: публичный репозиторий,
демонстрируемый без доступа к реальным данным.

Платформа декомпозирована на подпроекты; каждый получает свою спеку и план:

1. **Ядро + агент-аналитик** ← этот документ
2. Данные: агент очистки/валидации + коннекторы источников —
   KoboToolbox API, ona.io API, Microsoft SharePoint (файлы через
   Microsoft Graph API). Kobo и Ona близки по API (общая ODK-родословная),
   поэтому проектируются как один тип коннектора с двумя реализациями;
   SharePoint — отдельный тип (файловое хранилище, OAuth-авторизация)
3. Проектный контекст и формы: структурированный реестр индикаторов
   (`indicators.yaml`, извлекается агентом из логфрейма) + агент-дизайнер
   форм опроса. Формы — в формате **XLSForm** (единый стандарт Kobo и Ona;
   целевую платформу выбирает пользователь). Валидация форм — `pyxform`,
   без LLM; загрузка формы на платформу — через коннекторы подпроекта 2
4. Отчётность: агент-генератор отчётов (5W/MEAL/донорские шаблоны);
   опирается на реестр индикаторов из подпроекта 3
5. BI-инженер: агент с MCP-сервером powerbi-modeling (DAX, меры, модели)
6. Веб-UI и командное использование

Порядок подпроектов 2–4 может меняться; ядро идёт первым.

**Фундамент:** Claude Agent SDK (Python, пакет `claude-agent-sdk`).
Выбран за готовый агентный цикл, программные сабагенты (`AgentDefinition`),
in-process MCP-инструменты (`create_sdk_mcp_server`), нативное подключение внешних
MCP-серверов и блокирующие хуки (`PreToolUse`). Архитектура (роли, контракты,
PII-граница) проектируется фреймворко-независимо — переезд на другой оркестратор
не ломает дизайн.

**Языки:** рабочие документы (спеки, планы) — русский; код, комментарии, README
и всё видимое в публичном репозитории — английский (аудитория портфолио).

## 2. Цели и границы подпроекта 1

**Результат:** консольное приложение-чат. Пользователь указывает папку workspace
с данными (Excel/CSV, в т.ч. Kobo-экспорты), задаёт вопросы на русском или
английском («сколько бенефициаров по областям?», «есть ли дубли?», «сравни август
с июлем») и получает ответы с числами, таблицами и сохранёнными графиками.
Под капотом оркестратор делегирует запрос агенту-аналитику; тот пишет pandas-код,
код выполняется локально, агент интерпретирует результат.

Дополнительно в подпроект 1 входит **минимальная версия проектного контекста**:
папка `workspace/project_docs/` (проектные предложения, логфреймы, списки
индикаторов — PDF, DOCX, XLSX, MD) и инструменты чтения этих документов,
чтобы аналитик отвечал с учётом контекста проекта («какой у нас целевой
показатель по этому индикатору?»).

**Не входит в подпроект 1:** внешние источники данных (Kobo API, ona.io,
SharePoint — подпроект 2), отдельная роль очистки данных, реестр индикаторов
и дизайнер форм (подпроект 3), генерация отчётов, Power BI, веб-UI,
многопользовательность.

### Ключевые принципы (закладываются в ядро навсегда)

1. **PII-граница.** Сырые строки данных никогда не попадают в контекст LLM.
   Агент видит схему, статистики, агрегаты и результаты выполнения кода.
   Граница держится техническими средствами (хук + загрузчик + фильтр вывода),
   а не только промптом. Детали — раздел 5.
2. **Ядро отделено от интерфейса.** CLI — тонкая обёртка; будущий веб-UI
   подключается к тому же ядру без переписывания.
3. **Демо-режим с первого дня.** Генератор синтетического Kobo-подобного
   датасета в репозитории; реальные данные — только локально, вне git.
4. **Наблюдаемость.** Каждая сессия логирует вызовы агентов, выполненный код,
   токены и стоимость.

## 3. Архитектура и компоненты

```
┌─ CLI-чат (тонкий слой: ввод/вывод, рендеринг таблиц) ─┐
│                                                        │
│  ЯДРО                                                  │
│  ├─ Сессия: обёртка над ClaudeSDKClient,               │
│  │  сборка опций, бюджет, логирование                  │
│  ├─ Оркестратор (главный агент) ──delegates──▶ Агент-  │
│  │                                            аналитик │
│  ├─ PII-хук (PreToolUse): запрет прямого               │
│  │  чтения файлов данных                               │
│  └─ Инструменты данных (in-process MCP):               │
│     list_datasets / profile_dataset / run_analysis     │
│                          │                             │
└──────────────────────────┼─────────────────────────────┘
                           ▼
              Локальный сандбокс-исполнитель
              (pandas-код, только папка workspace,
               без сети, таймаут, фильтр вывода)
```

Шесть компонентов, у каждого одна обязанность:

| Компонент | Обязанность | Что НЕ делает |
|---|---|---|
| **CLI** (`cli/app.py`) | REPL-цикл, рендеринг ответов (таблицы, пути к графикам, счётчик расходов) | Не знает про агентов и SDK |
| **Сессия** (`core/session.py`) | Сборка `ClaudeAgentOptions` (агенты, инструменты, хуки, `max_budget_usd`), диалоговый цикл через `ClaudeSDKClient`. Единственная точка входа в ядро | Не содержит доменной логики |
| **Агенты** (`core/agents/`) | Оркестратор (понимает запрос, уточняет, делегирует) и аналитик (`AgentDefinition`: промпт с дисциплиной сеньор-аналитика — валидация перед выводами, SADD-дезагрегация, явные допущения; инструменты — только datatools). Реестр: новая роль = новый файл с определением | Агенты не читают файлы напрямую |
| **Инструменты данных** (`core/tools/`) | In-process MCP-сервер: `list_datasets`, `profile_dataset` (безопасный профиль без сырых строк), `run_analysis` (код → сандбокс → результат; включая сохранение графиков), `list_project_docs` и `read_project_doc` (чтение проектной документации из `project_docs/` в контекст; извлечение текста из PDF/DOCX — `pypdf`/`python-docx`) | Не выполняют код сами — только через сандбокс |
| **Сандбокс** (`core/sandbox/`) | Подпроцесс-исполнитель: доступ только к workspace, без сети, таймаут, лимит вывода; `loader.py` (загрузка датасета без PII-колонок), `guard.py` (фильтр вывода) | — |
| **Телеметрия** (`core/telemetry.py`) | JSONL-лог сессии: ходы, вызовы инструментов **и их результаты** (т.е. всё, что попало в контекст LLM), выполненный код, токены/стоимость из `ResultMessage` | — |

**PII-хук:** `PreToolUse`-хук блокирует Read/Grep/Bash по файлам данных
(`workspace/data/`) с сообщением «используй profile_dataset/run_analysis».
Отказ — штатное событие, агент перенаправляется на инструменты данных.
**Исключение:** `workspace/project_docs/` — документация предназначена
для чтения LLM, доступ через `read_project_doc` разрешён. Разделение
данных и документации — на уровне папок: `workspace/data/` (только через
сандбокс) и `workspace/project_docs/` (читается в контекст).

## 4. Поток данных (канонический сценарий)

Вопрос: «Сколько бенефициаров по областям за август, с разбивкой по полу?»

1. CLI → сессия → оркестратор. Аналитический запрос → делегирование аналитику.
2. Аналитик: `list_datasets` → `profile_dataset("beneficiaries.xlsx")`.
   При вопросах, требующих контекста проекта («как мы идём к целевому
   значению индикатора?»), — дополнительно `list_project_docs` →
   `read_project_doc("logframe.md")`.
   Профиль: колонки, типы, null-rate, значения категориальных колонок,
   диапазоны дат. Кэшируется на сессию.
3. Профилировщик размечает PII-колонки: эвристики по имени
   (`name/імʼя/прізвище/phone/тел/gps/lat/адрес…`) и по содержимому
   (регэкспы телефонов, координат). В профиле колонка видна
   («`resp_phone`, object, PII»), значения — никогда.
4. Аналитик пишет pandas-код и вызывает `run_analysis`. Код загружает данные
   через хелпер `load_dataset("beneficiaries")` — **по умолчанию без
   PII-колонок**.
5. Сандбокс выполняет код; вывод проходит фильтр: обрезка таблиц
   больше 50 строк, регэксп-скан на телефоны/координаты, лимит объёма 32 КБ.
   Таймаут выполнения — 60 секунд. Все три лимита конфигурируемы
   в `config.toml`; здесь указаны значения по умолчанию.
6. Аналитик проверяет адекватность результата (размеры групп, пропуски в поле
   «пол» — упомянуть в ответе), формулирует вывод.
7. Оркестратор → CLI (рендер таблицы) → телеметрия (код + стоимость).

## 5. Модель угроз PII

Идёт в README отдельным разделом. Защищаемся от **случайной** утечки PII в API,
не от злонамеренного агента. Четыре слоя:

1. Промпт-дисциплина (агент знает правила);
2. `PreToolUse`-хук (нет прямого чтения файлов данных);
3. Загрузчик `load_dataset` отдаёт датафрейм без PII-колонок;
4. Выходной фильтр сандбокса (обрезка построчных дампов, регэкспы
   телефонов/GPS, лимит объёма).

Известный обход: код в сандбоксе может прочитать файл напрямую
(`pd.read_excel`), минуя хелпер. Поэтому слои 4 и телеметрия (лог каждого
выполненного куска кода — аудируемость) обязательны. Если анализ действительно
требует PII-колонку — явный флаг с предупреждением (в v1 не реализуем,
фиксируем как осознанное ограничение).

**Осознанное исключение — проектная документация.** Содержимое
`workspace/project_docs/` читается в контекст LLM целиком: в этом его
назначение (агент должен понимать проект, индикаторы, целевые значения).
Ответственность за то, что положено в эту папку, — на пользователе;
README предупреждает: не класть туда файлы с данными бенефициаров.
Данные — в `workspace/data/`, документация — в `workspace/project_docs/`,
граница между ними техническая (хук + инструменты).

```
humanitarian-analytics-agents/

├─ src/haa/
│  ├─ core/
│  │  ├─ session.py
│  │  ├─ agents/              ← orchestrator.py, analyst.py, registry.py
│  │  ├─ tools/               ← datatools.py (MCP-сервер), profiler.py
│  │  ├─ sandbox/             ← executor.py, loader.py, guard.py
```

Имя пакета `haa` — рабочее, замена дешёвая.

(по умолчанию $2 — SDK останавливает работу при превышении), путь к workspace.

дешёвые роли (haiku/sonnet) появятся в следующих подпроектах.

## 7. Синтетический демо-датасет

`demo/generate_demo_data.py` (faker + numpy, фиксированный seed):
Kobo-подобный экспорт опроса домохозяйств, ~3000 строк:

- 8 прифронтовых областей, громады, тип поселения;
- SADD-поля: пол/возраст/инвалидность; статус перемещения;
- полученные услуги, удовлетворённость;
- **фейковые PII**: имена, телефоны, GPS, свободные комментарии
  (чтобы PII-граница была видна в демо);
- намеренные дефекты качества: дубли сабмишенов, пропуски в поле «пол»,
  возраст 999, разнобой написания областей, даты из будущего.

Генератор также создаёт **фейковый проектный документ** —
`project_docs/logframe.md` с индикаторами и целевыми значениями,
согласованными с демо-датасетом, — чтобы в демо был виден сценарий
«вопрос с учётом контекста проекта».

На этом датасете работают демо, юнит-тесты и smoke-eval.

## 8. Обработка ошибок

| Уровень | Поведение |
|---|---|
| Ошибка кода в сандбоксе | stderr → аналитику как результат инструмента; максимум 3 попытки исправить (счётчик в ядре, не в промпте); после — честный ответ, что и почему не вышло |
| Таймаут / превышение объёма вывода | те же правила: внятное сообщение агенту вместо трейсбека |
| Ошибки API | ретраи с бэкоффом — сам SDK; обрыв сети — сообщение + сохранённый лог сессии |
| Превышение `max_budget_usd` | аккуратная остановка: «потрачено $X, вот что успели» |
| Пользовательские ошибки (нет workspace, пустая папка, битый Excel) | дружелюбные сообщения в CLI до обращения к LLM (валидация на старте) |
| Срабатывание PII-хука | штатное событие: отказ с перенаправлением на инструменты; в итогах сессии — счётчик заблокированных попыток |

**Принцип честности** в промптах обоих агентов: не выдумывать числа; каждое
число в ответе происходит из выполненного кода; неуверенность проговаривается.
Телеметрия позволяет проверить происхождение любого числа.

## 9. Тестирование

Ключевая идея: **максимум логики тестируется без LLM**.

- **Юнит-тесты (ядро CI, без API-ключа):** профилировщик, PII-эвристики,
  фильтр вывода (телефоны/GPS редактируются, длинные таблицы режутся),
  загрузчик (PII-колонки выброшены), сандбокс (таймаут, лимит вывода,
  недоступность сети и файлов вне workspace), PII-хук (deny на Read
  в `workspace/data/`, allow для `workspace/project_docs/` и вне workspace),
  инструменты документации (извлечение текста из PDF/DOCX/XLSX/MD),
  телеметрия. Всё на демо-датасете с фиксированным seed.
- **Smoke-eval с LLM (`pytest -m api`, ручной запуск):** 5–7 канонических
  вопросов к демо-датасету; ожидаемые числа посчитаны в самом тесте обычным
  pandas. Проверяем, что агент приходит к тем же агрегатам. В CI не гоняем
  (стоит денег); запуск перед релизами.
- **CI (GitHub Actions):** ruff + юнит-тесты на каждый push. Без секретов.

Реализация — через TDD (тесты до кода) по процессу superpowers.

## 10. Критерии приёмки подпроекта 1

1. `uv run haa chat --workspace ./workspace` открывает работающий чат.
2. Демо-сценарий: сгенерировать демо-данные → задать канонический вопрос
   (раздел 4) → получить корректную таблицу агрегатов и сохранённый график.
3. Демо-сценарий с контекстом: вопрос «как мы идём к целевому значению
   индикатора X?» — агент читает `project_docs/logframe.md`, считает факт
   по данным и сравнивает с целевым значением.
4. Ни один вызов API за сессию не содержит сырых строк данных
   (проверяемо по логу телеметрии).
5. Юнит-тесты и ruff проходят в CI; smoke-eval проходит локально.
6. README: схема архитектуры, инструкция запуска демо, модель угроз PII
   (включая предупреждение о `project_docs/`).
