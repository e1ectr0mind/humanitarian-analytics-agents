# Дизайн: движок индикаторов + отчёты «прогресс по индикаторам» и 5W (ломоть 4a)

**Дата:** 2026-09-14
**Статус:** утверждён (секции 1–3 согласованы в брейншторм-сессии)
**База:** ядро (1) + коннекторы/чистильщик (2а) + реестр/дизайнер (3) +
SharePoint (2б) — в master

---

## 1. Контекст и решения брейншторма

Подпроект 4 платформы («Отчётность: агент-генератор отчётов 5W/MEAL/донорских
шаблонов; опирается на реестр индикаторов из подпроекта 3»). Пользователь
выбрал четыре типа отчётов: прогресс по индикаторам, 5W-матрица, донорский
нарратив, сводка по датасету. Четыре типа не помещаются в одну спеку, и шов
между ними проходит по природе содержимого:

- **4a (этот документ) — отчёты-данные:** фиксированная структура, числа
  считаются детерминированно. Прогресс по индикаторам и 5W.
- **4b (позже) — отчёты-проза:** нарратив и сводка; их пишет модель,
  цитируя числа, посчитанные движком 4a. docx-сборка — там же.

Ключевые решения:

- **Числа считает детерминированный движок, не LLM.** Рассматривались:
  (B) репортёр пишет pandas в песочнице, как чистильщик — минимум кода, но
  каждое число заново выводит LLM-код, невоспроизводимо и проверяется
  только платными эвалами; (C) движок как библиотека внутри песочницы —
  детерминированный путь спрятан за LLM-написанным glue-кодом. Выбран
  вариант (A): движок как чистая библиотека + MCP-сервер + CLI, агент
  только оркестрирует. Это и есть «детерминированный движок», который
  спека SP3 сознательно отложила («схема уже готова»).
- **Структура 5W — маппинг-файл `workspace/5w.yaml`**, который репортёр
  предлагает по профилю датасета, пользователь правит руками, движок
  потребляет. Тот же паттерн, что `indicators.yaml`. Альтернативы —
  зашитый лейаут OCHA (любое отличие реального шаблона правится руками
  после выгрузки) и заполнение чужого xlsx-шаблона кластера (много работы и
  хрупкости: объединённые ячейки, многоуровневые шапки) — отклонены.
- **Форматы выхода — xlsx + markdown.** xlsx — то, что реально уходит
  кластеру/донору; markdown — читаемо в чате, диффится в git, сырьё для
  нарратива 4b. CSV и docx — не в 4a.
- **Побочный бонус:** инструмент `compute_indicators` отдаётся и аналитику
  — вопрос «какой прогресс по 1.1?» получает детерминированный ответ вместо
  самописного pandas (усиливает критерий приёмки 2 из SP3).

## 2. Цели и границы

**Возможность 1 — движок расчёта индикаторов.** Детерминированно
вычисляет каждый индикатор реестра, у которого есть `measure`: факт по
всему датасету плюс разбивка по каждому измерению из `disaggregation`.
Индикаторы без `measure` попадают в отчёт со статусом «не вычислим — нет
measure-блока» и никогда не угадываются.

**Возможность 2 — отчёт о прогрессе по индикаторам.** Таблица «код /
название uk+en / цель / факт / % выполнения», ниже — таблицы дезагрегаций.
Выход: `reports/indicators_<YYYY-MM-DD>.md` + `.xlsx` (лист «Summary» +
лист на каждое измерение дезагрегации).

**Возможность 3 — 5W-матрица** по `workspace/5w.yaml`. Выход:
`reports/5w_<YYYY-MM-DD>.md` + `.xlsx`.

**UX-потоки:**

1. «Сделай отчёт о прогрессе по индикаторам» → оркестратор → **reporter**
   → `read_indicators` → `build_indicator_report` → ответ: какие индикаторы
   посчитаны, какие нет и почему, пути к файлам.
2. «Сделай 5W за август» → reporter: если `5w.yaml` нет — смотрит
   `profile_dataset` и логфрейм (организация, проект), **предлагает**
   маппинг, сохраняет через `save_5w_mapping` (схемная валидация), затем
   `build_5w`. Если маппинг уже есть — сразу сборка. Файл правится руками.
3. **CLI без LLM:** `haa report indicators [--period START..END --date-field F]`,
   `haa report 5w [--period …]` — как `haa pull`, ключ API не нужен.
4. **Аналитик** получает `compute_indicators`: на «какой прогресс по 1.1?»
   отвечает числом движка.

**Три решения по данным:**

- **Чистая копия предпочтительна.** Если рядом с датасетом есть
  `<dataset>_clean.xlsx`, движок берёт её и пишет это в шапку отчёта;
  иначе — сырой файл, тоже с пометкой. Отчитываться по чистым данным —
  норма MEAL.
- **Отчётный период** — необязательный блок `{field, start, end}`: если
  задан, применяется как глобальный фильтр по дате до расчёта и печатается
  в шапке; если нет — все записи, и шапка так и говорит. Отчёт с подписью
  «июнь–август», посчитанный по всему массиву, — ошибка, которую
  конструкция не допускает.
- **PII-страж:** движок отказывается считать по PII-колонке — в
  `measure.field`, в `disaggregation`, в группировке 5W — с внятным
  объяснением. Детектор — тот же, что у профайлера.

**Не входит в 4a:** нарратив и сводка (4b), docx, графики в отчётах,
индикаторы «меньше — лучше», baseline, индикаторы на нескольких датасетах,
заполнение чужих xlsx-шаблонов, запуск по расписанию, CSV.

**PII-граница.** Движок работает in-process на локальных файлах и выдаёт
только агрегаты; инструменты возвращают агрегаты и пути, никогда — строки
данных. Файлы отчётов лежат в `reports_dir` (агрегаты, не данные
бенефициаров). Остаточный риск малых ячеек при дезагрегации — стандартная
MEAL-осторожность, контролируется пользователем.

## 3. Архитектура и компоненты

```
src/haa/
├─ reporting/                  ← НОВОЕ: чистая логика, ноль LLM (как forms/)
│  ├─ engine.py                ← resolve_dataset (clean-предпочтение), period-фильтр,
│  │                              evaluate_registry(registry, workspace, period) → ReportRun
│  ├─ fivew.py                 ← validate_mapping(dict) → адресные ошибки; build_5w(df, mapping)
│  ├─ storage.py               ← load/save workspace/5w.yaml (зеркало indicators/registry.py)
│  └─ render.py                ← markdown + xlsx (openpyxl) для обоих видов отчётов
├─ core/tools/reporttools.py   ← четвёртый MCP-сервер "reports": ReportToolbox
├─ core/agents/reporter.py     ← REPORTER_PROMPT + build_reporter (четвёртая роль)
├─ core/agents/registry.py     ← + reporter (четыре роли)
├─ core/agents/orchestrator.py ← маршрутизация: отчёт / 5W / звіт → reporter
├─ core/agents/analyst.py      ← += mcp__reports__compute_indicators
├─ core/session.py             ← проводка reports-сервера
├─ cli/app.py                  ← haa report indicators|5w
└─ config.py                   ← + reporter_model
```

**Семантика движка** (по схеме `measure` из SP3, теперь с точными
определениями):

| aggregation | значение |
|---|---|
| `count` | строк после `filter`; при заданном `field` — непустых значений поля |
| `count_unique` | уникальных непустых `field` после `filter` |
| `sum` | сумма `field` после `filter`; нечисловое поле → «не вычислим» |
| `percent` | `numerator` / `denominator` × 100, где каждый — уникальные непустые `field` после своего `filter`; знаменатель 0 → «не вычислим» |

- **Дезагрегация:** для каждого измерения из `disaggregation` — группировка
  по колонке, measure применяется внутри каждой категории (для `percent`
  числитель и знаменатель оба ограничены категорией); категории в порядке
  имён, пропуски — строка `(missing)` последней.
- **Период** `{field, start, end}` применяется до всего остального (даты
  парсятся с `errors="coerce"`); строки с неразбираемой датой исключаются,
  их число печатается в шапке.
- **Прогресс** = факт / цель × 100 (1 знак после запятой) при наличии
  `target`; направление «больше — лучше» — ограничение v1, записано явно.
- **Статус «не вычислим»** с причиной: нет `measure`; датасет / колонка не
  найдены; ошибка `filter`-запроса; нечисловая сумма; нулевой знаменатель;
  PII-колонка.

**Модель результата:** `IndicatorResult(code, name, target, unit, actual,
progress_pct, breakdowns: {dimension: [BreakdownRow]}, status, reason,
dataset)`; `ReportRun(period, sources: {dataset: SourceInfo(path,
used_clean, rows_in_scope, rows_excluded_by_period)}, results)`. Разные
индикаторы могут ссылаться на разные датасеты — каждый датасет
резолвится и фильтруется один раз, шапка отчёта перечисляет все
источники; один индикатор поверх нескольких датасетов — не в 4a.

**Схема `workspace/5w.yaml`** (строгая: неизвестные ключи на всех уровнях
отклоняются — урок SP3):

```yaml
dataset: beneficiaries
fixed:                          # Who + проект: константы в каждой строке
  Organization: IMC
  Project: ABC-123
where: [oblast, raion, hromada] # колонки датасета → одноимённые колонки 5W
when: {field: submission_date, granularity: month}   # month | none
what: {field: services_received, split: " "}         # split опц.: многозначное → строка на активность
whom:
  id_field: _uuid               # уникальные домогосподарства
  disaggregation: [head_sex]    # опц. → колонки head_sex=female / =male / =(missing)
```

Строка 5W = группа (where + период + активность); при
`granularity: none` колонки «Period» нет и группировка идёт без времени;
«Beneficiaries» = уникальные `id_field` в группе; колонки дезагрегации — уникальные
`id_field` в группе с данной категорией. Со `split` домохозяйство с
`cash health` учитывается в обеих строках — стандартная семантика 5W
(охват по активностям); подвал отчёта отдельно печатает уникальный охват,
чтобы сумму по строкам не приняли за него. Период 5W — те же три
аргумента, что у индикаторов (по умолчанию поле `when.field`).

**Рендер:** markdown — шапка (датасет, путь и clean/raw, период, строк в
охвате и исключённых), сводная таблица, список «не вычислим», таблицы
дезагрегаций по индикаторам; xlsx — лист «Summary» + лист на измерение
(индикаторы) или один лист «5W»; шапка жирным, закреплённая строка.
Markdown 5W ограничен 200 строками с пометкой, xlsx — полный. Имена:
`reports/indicators_<YYYY-MM-DD>.{md,xlsx}`, `reports/5w_<YYYY-MM-DD>.{md,xlsx}`
— повтор в тот же день перезаписывает.

**Сервер `reports`** (5 инструментов): `compute_indicators` (сводка
текстом, без файлов), `build_indicator_report`, `read_5w_mapping`,
`save_5w_mapping(yaml_text)` (валидация → адресные ошибки, файл не
пишется при ошибках), `build_5w`. Период — необязательные аргументы
`date_field / start / end`: `start` и `end` только вместе; для
индикаторов `date_field` обязателен вместе с ними, для 5W по умолчанию
берётся `when.field` из маппинга. Возвращают агрегаты и пути.

**Роль reporter:** reports-инструменты + `mcp__forms__read_indicators` +
`mcp__data__list_datasets` / `profile_dataset` + `list_project_docs` /
`read_project_doc`; **без `run_analysis`** — числа только из движка.
Дисциплина промпта: каждая цифра ответа — из вывода инструмента; «не
вычислим» объясняется и адресуется дизайнеру (правка реестра); маппинг
предлагается только из реальных имён колонок после `profile_dataset`;
перезапись существующего `5w.yaml` — только с подтверждения; PII в
маппинге никогда. Модель — `config.reporter_model` (по умолчанию как у
дизайнера).

**Маршрутизация:** «сделай отчёт / 5W / звіт / report» → reporter; «какое
значение / прогресс по 1.1» — аналитик через `compute_indicators`.

**Доступы ролей:** reporter — как выше; analyst += `compute_indicators`;
cleaner, designer — без изменений.

**Телеметрия:** `report_built` (kind, computed, not_computable, rows,
paths), `mapping_saved` (columns). Новых зависимостей нет: pandas, openpyxl,
PyYAML уже в проекте.

## 4. Потоки

**Отчёт по индикаторам:** `load_registry` → для каждого индикатора
`resolve_dataset` (clean-предпочтение) → period-фильтр → measure → breakdowns
→ `ReportRun` → `render` (md + xlsx) → телеметрия → сводка + пути.
Индикаторы без `measure`/с ошибкой не прерывают отчёт — попадают в него со
статусом.

**5W:** `load_mapping` (или ошибка «маппинга нет») → `validate_mapping` →
`resolve_dataset` → period → PII-страж на where/what/whom.disaggregation →
`split` активностей → группировка → уникальный охват → `render` →
телеметрия → сводка (строк, колонок, уникальный охват) + пути.

**Предложение маппинга (только через агента):** reporter →
`profile_dataset` → `read_project_doc` (организация/проект) → YAML →
`save_5w_mapping` → ошибка валидации → правка → повтор → `build_5w`.

**CLI:** `haa report …` строит `ReportToolbox` с телеметрией
`cli-report-<stamp>.jsonl` (паттерн `haa pull`) и печатает сводку.

## 5. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| реестр пуст / отсутствует | «реестр индикаторов пуст — попросите извлечь индикаторы из логфрейма» |
| индикатор без `measure` | строка в отчёте со статусом «не вычислим: нет measure-блока — дополните реестр (дизайнер)»; отчёт строится |
| датасет из `measure.dataset` не найден | статус «не вычислим: датасет X не найден; доступны: …» — по индикатору, не по отчёту |
| колонка `field` / `disaggregation` отсутствует | статус с именем колонки и подсказкой «проверьте profile_dataset» |
| ошибка `filter`-запроса pandas | статус с первой строкой ошибки query |
| PII-колонка в `field` / `disaggregation` / 5W-группировке | отказ по конкретному элементу: «колонка X помечена как персональные данные — агрегация по ней запрещена» |
| период: поле не найдено | отчёт не строится, подсказка с доступными колонками |
| период: часть дат не разбирается | строки исключены, число в шапке |
| `5w.yaml` невалиден | адресные ошибки (`where[1]: expected a column name`, `unknown key 'sector'`), файл не записывается |
| `build_5w` без маппинга | «маппинга 5W нет — попросите репортёра предложить его» |
| ноль строк в охвате после периода | отчёт строится с нулями и явным предупреждением в шапке |
| всё прочее | паттерн 2а: дружелюбные строки, не трейсбеки |

## 6. Тестирование

- **Офлайн (масса, без LLM):** движок на демо-датасете с известными
  ответами (генератор детерминирован: 3 000 уникальных `_uuid`, 30 дублей,
  3 % пропусков `head_sex`, 999-возраста) — все четыре агрегации, `percent`
  с фильтрами, дезагрегация по `oblast` / `head_sex` включая `(missing)`,
  период с исключёнными датами, каждый класс «не вычислим»,
  clean-предпочтение (создать `_clean.xlsx` → шапка это отражает),
  PII-страж; `validate_mapping` — позитив + каждый класс ошибки +
  неизвестные ключи; `build_5w` — группировка, `split`, колонки
  дезагрегации, уникальный охват в подвале; golden-тесты рендера: md
  читается обратно и содержит точные числа, xlsx читается openpyxl (имена
  листов, шапки, значения); ReportToolbox напрямую (паттерн FormToolbox);
  CLI-парсер и `haa report` без API; проводка сессии, маршрутизация, четыре
  роли; промпт репортёра несёт дисциплину.
- **API-эвалы (2, ручные, метка `api`):** «Сделай отчёт о прогрессе по
  индикаторам» на демо-воркспейсе с реестром из SP3 → xlsx и md существуют,
  факт по 1.1 = 3 000 и % цели совпадают с независимым pandas в тесте,
  телеметрия содержит `report_built` и **не содержит** `run_analysis` от
  репортёра; «Сделай 5W» без маппинга → `5w.yaml` создан и проходит
  `validate_mapping`, xlsx содержит колонки `where` и ненулевые
  бенефициары, уникальный охват = 3 000.
- CI без изменений.

## 7. Критерии приёмки

1. `haa report indicators` без LLM на демо-воркспейсе с реестром SP3
   (1.1 `count_unique`, 1.2 `percent`, 2.1 без `measure`; демо-генератор
   реестр не пишет — его кладёт тест или дизайнер) →
   `reports/indicators_<дата>.md` + `.xlsx`; 1.1 и 1.2 посчитаны (3 000;
   доля женщин-глав совпадает с независимым расчётом), 2.1 — статус «не
   вычислим» с причиной.
2. Отчёт с периодом печатает период и число исключённых строк; без периода
   — «все записи».
3. При наличии `beneficiaries_clean.xlsx` шапка указывает чистую копию.
4. `haa report 5w` по валидному `5w.yaml` → md + xlsx с колонками маппинга
   и уникальным охватом в подвале; невалидный маппинг — адресные ошибки,
   файлы не пишутся.
5. Репортёр через чат строит оба отчёта; в его телеметрии нет
   `run_analysis`; аналитик отвечает на «прогресс по 1.1» через
   `compute_indicators`.
6. Офлайн-тесты и ruff зелёные в CI; api-эвалы проходят локально.

## Постскриптум 2026-09-14: приёмка и доработки

API-эвалы `-k "reporter or indicator_progress"`: 3 passed (2026-09-14).

После финального ревью в код внесены правки, которые заменяют часть текста
спеки выше:

- Список разрешённых фильтров уже, чем в §3: сравнения, `and`/`or`/`&`/`|`/
  `~`, списки `in [...]` и `.isin([...])`, `.isna()`/`.notna()`,
  `.str.contains`/`.str.startswith`/`.str.endswith` с обычным текстом
  (в `contains` разрешена альтернатива через `|`) — арифметика запрещена;
  выражение фильтра обязано быть построчным условием, а не голой колонкой
  или константой.
- Строка §5 «ошибка filter-запроса → первая строка ошибки query» заменена
  фиксированным дружелюбным предложением без текста pandas.
- Отказы по PII называют следующий шаг (выбрать другую колонку или
  переименовать её в чистой копии) и распространяются также на колонку
  периода.
- Значения категорий в тексте для LLM показываются только для колонок,
  которые профайлер показал бы в `profile_dataset` (≤ 30 уникальных
  значений по полному датасету, а не по периоду).
- Чистая копия старше сырого файла — отчёт всё равно строится по чистой
  копии, но с предупреждением (решение пользователя).
- Числовая колонка даты даёт дружелюбную ошибку вместо пустого периода.
- 5W-отчёт сообщает обо всех непригодных колонках маппинга сразу (не по
  одной) и сортирует `(missing)` последним среди значений ключевых колонок.
- Текст ячейки xlsx, начинающийся с `=`, всегда сохраняется как текст, а
  не как формула.
- Лист «About» в xlsx перечисляет ошибки по разбивкам (breakdown errors),
  а недопустимые для xlsx символы вырезаются из значений ячеек и имён
  листов.
- `haa report` завершается кодом 1, если отчёт не был построен, и кодом 0
  при успехе.
- Дезагрегация 5W (`whom.disaggregation`) принимает только колонки с не
  более чем 30 уникальными значениями по полному датасету; колонка вроде
  `_uuid` попадает в общую ошибку о непригодных колонках маппинга (иначе
  сводная таблица растёт как N² и исчерпывает память).
- Фильтр длиннее 2000 символов отклоняется до разбора; слишком глубокая
  вложенность — дружелюбный отказ, а не `MemoryError`.
- Разбивка индикатора по колонке с более чем 2000 категориями не считается:
  записывается ошибка разбивки, итоговое значение не меняется.
- Числа внутри текстовой колонки даты (например, неформатированный
  серийный номер даты Excel) считаются записями без валидной даты, а не
  датами 1970 года.
